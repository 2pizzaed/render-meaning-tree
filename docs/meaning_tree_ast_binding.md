# Связывание Runtime Событий с Meaning-Tree AST

## Обзор

Meaning-Tree AST - это универсальный формат AST, который используется для построения CFG и генерации вопросов. Он отличается от стандартного Python AST структурой узлов и их типами.

## Структура Meaning-Tree AST

### Основные характеристики

1. **Узлы имеют уникальные ID**: Каждый узел имеет поле `id` (число) и `unique_hash`
2. **Иерархия узлов**: Узлы связаны через `parent` и `parent_field`
3. **Связь с исходным кодом**: Через `source_map` с полем `byte_positions`, которое связывает `ast_id` с позициями в исходном коде
4. **Типы узлов отличаются от Python AST**: Например, `function_call`, `return_statement`, `if_statement`, `le_operator` и т.д.

### Пример структуры узлов

#### Function Call (вызов функции)
```json
{
  "type": "function_call",
  "function": {
    "type": "identifier",
    "name": "fib",
    "repr_name": "fib",
    "id": 14
  },
  "arguments": [...],
  "id": 18,
  "unique_hash": -260927749
}
```

**Путь к имени функции**: `function.name`

#### Return Statement (возврат)
```json
{
  "type": "return_statement",
  "expression": {...},
  "id": 10,
  "unique_hash": -2080459641
}
```

#### Condition (условие в if)
```json
{
  "type": "if_statement",
  "branches": [
    {
      "condition": {
        "type": "le_operator",  // n <= 2
        "id": 8,
        "unique_hash": -1534399866
      },
      "body": {...}
    }
  ],
  "id": 13
}
```

**Путь к условию**: `if_statement.branches[].condition.id`

## Текущая реализация связывания

### 1. Условия (Conditions)

**Реализовано в**: `build_line_to_ast_id_for_conditions()`

**Алгоритм**:
1. Проходим по всем узлам в `nodes_cache`
2. Для `if_statement`: извлекаем `branches[].condition.id`
3. Для `while_statement`: извлекаем `condition.id`
4. Используем `get_code_line_number_by_id()` для получения номера строки
5. Создаём маппинг `{line_number: ast_id}`

**Статус**: ✅ Работает корректно

### 2. Вызовы функций (Function Calls)

**Реализовано в**: `_find_ast_id_for_event()` для `function_call`

**Текущий алгоритм**:
1. Ищем узлы типа `function_call` на строке `call_line` (или `line_number`)
2. Если на строке несколько узлов, используем первый найденный
3. Если не найдено, пробуем диапазон ±2 строки вокруг `call_line`
4. Если всё ещё не найдено, возвращаем первый найденный `function_call` в AST

**Проблемы**:
- ❌ Не учитывается имя функции при сопоставлении
- ❌ Может выбрать неправильный узел, если на строке несколько вызовов
- ❌ Для первого вызова из модуля верхнего уровня `call_line` может быть неправильным

**Улучшение**: ✅ Добавлено сопоставление по имени функции

### 3. Возвраты (Function Returns)

**Реализовано в**: `_find_ast_id_for_event()` для `function_return`

**Текущий алгоритм**:
1. Ищем узлы типа `return_statement` на строке `line_number`
2. Если на строке несколько узлов, используем первый найденный

**Проблемы**:
- ❌ Не учитывается контекст функции (может быть несколько return в разных функциях)
- ❌ Может выбрать неправильный узел при рекурсии

## Предложения по улучшению связывания

### Вариант 1: Использование имени функции + строка (рекомендуется)

**Для вызовов функций**:
```python
def _find_ast_id_for_function_call(event: FunctionCall, ast_analyzer: ASTNodeAnalyzer) -> int | None:
    """Находит ast_id для вызова функции с учётом имени функции."""
    candidates = []
    
    # Ищем все function_call узлы на строке call_line
    for ast_id, node in ast_analyzer.nodes_cache.items():
        if node.get('type') != 'function_call':
            continue
            
        node_line = ast_analyzer.get_code_line_number_by_id(ast_id)
        if node_line != event.call_line:
            continue
        
        # Проверяем имя функции
        func_node = node.get('function', {})
        if isinstance(func_node, dict):
            func_name = func_node.get('name')
            if func_name == event.function_name:
                candidates.append((ast_id, node))
    
    if candidates:
        return candidates[0][0]
    
    # Fallback: ищем по line_number функции, если call_line не сработал
    # ...
```

**Преимущества**:
- ✅ Точное сопоставление по имени функции
- ✅ Учитывает контекст вызова
- ✅ Работает для рекурсивных вызовов

**Недостатки**:
- ⚠️ Требует корректный `call_line` (может быть проблемой для первого вызова)

### Вариант 2: Использование стека вызовов

**Идея**: Отслеживать стек вызовов функций и использовать его для сопоставления.

**Для возвратов**:
```python
def _find_ast_id_for_function_return(
    event: FunctionReturn, 
    ast_analyzer: ASTNodeAnalyzer,
    call_stack: list[str]  # Стек имён функций
) -> int | None:
    """Находит ast_id для возврата с учётом стека вызовов."""
    # Ищем return_statement в контексте текущей функции
    current_func = call_stack[-1] if call_stack else None
    
    candidates = []
    for ast_id, node in ast_analyzer.nodes_cache.items():
        if node.get('type') != 'return_statement':
            continue
        
        node_line = ast_analyzer.get_code_line_number_by_id(ast_id)
        if node_line != event.line_number:
            continue
        
        # Проверяем, что return принадлежит нужной функции
        # (можно проверить через parent -> function_definition)
        if _belongs_to_function(ast_id, current_func, ast_analyzer):
            candidates.append((ast_id, node))
    
    return candidates[0][0] if candidates else None
```

**Преимущества**:
- ✅ Точное сопоставление для рекурсивных вызовов
- ✅ Учитывает контекст выполнения

**Недостатки**:
- ⚠️ Требует отслеживание стека вызовов
- ⚠️ Сложнее реализация

### Вариант 3: Использование уникальных хешей

**Идея**: Использовать поле `unique_hash` для более точного сопоставления.

**Проблема**: `unique_hash` вычисляется на основе структуры узла, но может не учитывать контекст выполнения.

**Статус**: ⚠️ Не рекомендуется как основной метод, но может быть дополнительной проверкой

### Вариант 4: Последовательное сопоставление (текущий подход)

**Идея**: События упорядочены по времени выполнения, узлы в AST упорядочены по порядку в коде.

**Алгоритм**:
1. Поддерживаем счётчик использованных узлов каждого типа
2. При поиске ast_id берём следующий неиспользованный узел соответствующего типа на нужной строке

**Преимущества**:
- ✅ Простая реализация
- ✅ Работает для последовательных вызовов

**Недостатки**:
- ❌ Не работает для параллельных/вложенных вызовов
- ❌ Требует отслеживание состояния

## Рекомендуемый подход

### Комбинированный метод

1. **Для условий**: Использовать текущий метод (через `line_to_ast_id`) ✅
2. **Для вызовов функций**: 
   - Сначала искать по `call_line` + имя функции ✅ (уже добавлено)
   - Если не найдено, искать по `line_number` функции + имя функции
   - Если всё ещё не найдено, использовать последовательное сопоставление
3. **Для возвратов**:
   - Искать по `line_number` + контекст функции (через parent)
   - Если несколько кандидатов, использовать последовательное сопоставление

### Улучшения для надежности

1. **Добавить валидацию**: После связывания проверять, что найденный узел действительно соответствует событию
2. **Логирование**: Логировать случаи, когда связывание не удалось или нашло несколько кандидатов
3. **Fallback механизмы**: Несколько уровней fallback для повышения надежности

## Примеры связывания

### Пример 1: Простой вызов функции

**Исходный код**:
```python
x = fib(5)  # строка 7
```

**Runtime событие**:
```python
FunctionCall(
    function_name="fib",
    line_number=1,  # строка определения функции
    call_line=7,    # строка вызова
    local_vars={"n": 5}
)
```

**Meaning-Tree AST**:
```json
{
  "type": "function_call",
  "function": {"name": "fib"},
  "id": 32,
  // byte_positions: строка 7
}
```

**Связывание**: `call_line=7` + `function_name="fib"` → `ast_id=32` ✅

### Пример 2: Рекурсивный вызов

**Исходный код**:
```python
return fib(n - 1) + fib(n - 2)  # строка 4
```

**Runtime события**:
```python
# Первый вызов
FunctionCall(function_name="fib", call_line=4, local_vars={"n": 4})
# Второй вызов (после возврата первого)
FunctionCall(function_name="fib", call_line=4, local_vars={"n": 3})
```

**Meaning-Tree AST**:
```json
{
  "type": "add_operator",
  "left_operand": {
    "type": "function_call",
    "function": {"name": "fib"},
    "id": 18  // первый вызов
  },
  "right_operand": {
    "type": "function_call",
    "function": {"name": "fib"},
    "id": 23  // второй вызов
  }
}
```

**Связывание**: 
- Первый вызов: `call_line=4` + `function_name="fib"` → `ast_id=18` ✅
- Второй вызов: `call_line=4` + `function_name="fib"` → `ast_id=23` ✅
- Проблема: Оба на одной строке! Нужно последовательное сопоставление.

### Пример 3: Условие в if

**Исходный код**:

## Проблемные случаи

### Проблема 1: Первый вызов из модуля верхнего уровня

**Симптом**: `call_line` указывает на неправильную строку (например, на строку определения функции вместо строки вызова)

**Решение**: 
- Использовать `line_number` функции как fallback
- Искать в диапазоне строк вокруг `call_line`
- Использовать последовательное сопоставление

### Проблема 2: Несколько вызовов на одной строке

**Симптом**: `fib(n-1) + fib(n-2)` - два вызова на одной строке

**Решение**:
- Использовать последовательное сопоставление
- Отслеживать порядок использования узлов

### Проблема 3: Рекурсивные вызовы с одинаковыми параметрами

**Симптом**: Несколько вызовов одной функции с одинаковыми аргументами на одной строке

**Решение**:
- Использовать порядок выполнения (order из runtime событий)
- Сопоставлять последовательно по порядку

## Рекомендации по реализации

1. **Приоритет методов связывания**:
   ```
   1. call_line + function_name (для вызовов)
   2. line_number + function_name (fallback)
   3. Последовательное сопоставление (если несколько кандидатов)
   4. Первый найденный (последний fallback)
   ```

2. **Валидация**:
   - После связывания проверять соответствие имени функции
   - Логировать случаи неоднозначности

3. **Кэширование**:
   - Кэшировать результаты связывания для повторного использования
   - Инвалидировать кэш при изменении AST

4. **Обработка ошибок**:
   - Если связывание не удалось, возвращать `None` (не падать)
   - Логировать предупреждения для отладки
